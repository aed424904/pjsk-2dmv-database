# 数据更新流水线加固设计

## 目标

在保留现有“Python 数据脚本 + 静态网页”架构的前提下，让一次更新要么完整成功并发布，要么保持上一版可用数据不变；同时避免不完整播放列表、历史快照重复改写和项目根目录被本地服务器公开。

## 方案选择

采用渐进式事务化方案。所有生成脚本支持由 `PROJECT_SEKAI_OUTPUT_DIR` 指定输出目录，`auto_update.py` 在项目内创建临时输出目录，按 `musics_base -> database_v2 -> combined_music_data -> validate` 的顺序生成和校验。只有全部步骤成功后，才把七个正式产物替换到 `output/`；发布过程中发生异常时恢复旧文件。

相比只调整 GitHub Actions 顺序，这能覆盖本地双击更新时的半成品风险；相比引入 Node 构建器或数据库迁移框架，改动更小，也不会改变现有数据格式和使用习惯。

## 数据流与错误处理

播放列表抓取完成后，若新条目数比当前有效快照下降超过 20%，视为疑似分页/API 异常，保留旧快照并报告失败。手工执行的频道补全脚本只处理各来源的最新有效快照，并且仅在视频字段确有变化时写盘。

GitHub Actions 使用真实子模块检出，先运行单元测试，再执行统一更新入口，最后复验数据库和构建显式白名单的 `dist/`。部署与本地服务器都只使用 `dist/`，不再公开 `.git`、备份、测试和脚本目录。本地服务器绑定 `127.0.0.1`。

## 校验与兼容性

现有数据库结构保持兼容。验证器新增顶层类型、必填值、统计分布、视频类型、YouTube ID/URL 和重复 ID 检查；无法匹配 Sekai ID 的歌曲继续允许存在，以兼容新视频先于游戏主库出现的情况。

测试覆盖异常快照拒绝、暂存发布回滚、输出目录重定向、深度数据校验和站点白名单。现有 54 个测试必须继续通过。
