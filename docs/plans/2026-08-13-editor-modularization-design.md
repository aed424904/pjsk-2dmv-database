# 统一编辑器模块化设计

## 背景与目标

`editor.html` 已统一承载视频补录与别称维护，但样式、共享函数、两套业务逻辑和启动代码仍集中在一个近 2400 行的 HTML 文件中。这会让小改动的审查范围过大，也容易在处理某个编辑器时误伤另一个。

本阶段只做结构性重构：不改 JSON 格式、页面布局、文案、全局对象名或旧链接行为。成功标准是 `editor.html` 只保留语义化页面骨架与资源引用，业务代码按职责位于 `assets/` 下，并且真实浏览器行为与拆分前一致。

## 方案比较与决策

1. **经典脚本按职责拆分（采用）**：拆为 `editor.css`、`editor_shared.js`、`manual_video_editor.js`、`alias_editor.js` 和 `editor_bootstrap.js`，使用普通 `<script src>` 按顺序加载。它不需要打包器，可以完整保留现有 `ManualVideoEditor` 和 `AliasEditor` 全局接口，风险最低。
2. **只拆成一个 CSS 和一个 JS**：变更最小，但视频与别称逻辑仍然耦合在一个大文件里，无法达成维护性目标。
3. **ES Modules 与精细依赖导入**：长期边界最清晰，但会同时改变作用域、文件协议兼容和加载时机，对这个无构建工具的静态站点属于过度设计。

## 架构与加载顺序

`editor.html` 先加载 `editor.css`，页面末尾按固定顺序加载四个脚本：共享工具 → 视频编辑器 → 别称编辑器 → 启动器。启动器是唯一个主动初始化页面的模块；前三个脚本只定义现有全局能力。这个顺序通过静态测试锁定，避免未来调整 HTML 时产生偶发的未定义错误。

站点构建白名单同步增加这五个资源。如果任意文件缺失，`build_site.py` 继续在发布前立即失败，而不是构建一个浏览器打开后才报错的不完整站点。

## 验证与风险控制

自动测试检查 HTML 不再包含大段内联 CSS/JS、资源引用顺序、两个命名空间与 URL 标签逻辑仍存在，以及所有新资源都进入 `dist/`。浏览器验收覆盖视频补录、别称编辑、标签切换、旧入口跳转、桌面端与移动端宽度，并收集页面脚本错误。

主要风险是机械搬移时丢失括号、改变加载顺序或少发布一个资源。因此实施不重写业务代码，只搬移原有代码块；拆分前后使用脚本内容指纹、自动测试与真实浏览器三层校验。
